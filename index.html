Abang builds durable, inspectable tools for working with AI. It starts with a runtime that records every step of a run, and the same habit carries through the rest: whatever the tool did, it leaves a record you can replay or check instead of guessing at it. Everything runs on your own machine. Two products ship today and four are still in the kitchen.

What we build

Six products, labelled honestly. Two you can install today. The other four are here because we intend to build them, not because any of them is ready.

satay

Alpha

A durable execution runtime for async Python. Write ordinary async def workflows, and every durable call lands in an append-only journal, so a crashed run replays from the top and reuses what already finished.

It also ships a local debugger: fork a run from any point and compare two runs call by call. On PyPI now at 0.1.0a3, and the docs are honest about what's missing.

sibei-flow

Available

An AI SRE for data pipelines. When a dbt or Airflow job breaks, sbflow reads the failing model, drafts the smallest fix that works, verifies it in a throwaway sandbox, and opens a pull request with the diff, an explanation and its evidence.

Four deterministic gates decide whether you ever see a draft. It holds no prod-write credentials, so merging is the approval and git revert is the rollback.

kopicode

Planned

A coding agent for the terminal, written in Go and shipped as a single binary. It keeps its own append-only record of a session, every message, tool call and permission decision, and snapshots the working tree to a git ref after each turn, so forking at the turn where things went wrong rewinds your files along with the conversation.

It does not run on satay. A durable-execution journal records what the agent decided, not what happened to your repo, so a replayed fork would rewind the conversation over a working tree that never moved. git versions the files; the journal records why.

Built on satay

sotong

Planned

An assistant that runs on your own machine, always on, reachable from the places you already type. It acts on schedules and triggers rather than waiting to be opened. Nothing is built yet and there is no timeline.

It stays a separate product from kopicode rather than a mode of it, because something that acts while nobody is watching needs a stricter safety model than something you're supervising. It is also where satay fits: a run that dies overnight has nobody to retype the prompt, and replay is built for that.

Phase 0 · a benchmark, not the product

tingkat

Research

A control plane for teams serving many LoRA adapters on GPUs they run themselves. The bet is that sending each request to a replica that already holds its adapter beats round-robin: fewer cold starts, a shorter tail, the same hardware.

Phase 0 tests that bet before any of the product is built. It is a discrete-event simulator, no vLLM and no GPUs, running the same seeded workload through both routing strategies. At 16 replicas, affinity routing cut cold starts by 89% against round-robin, clearing the 80% gate the PRD set. On an eight-replica fleet at 85% utilisation, p99 time-to-first-token improved by 47%. Affinity costs you some load imbalance, and the README shows that column rather than hiding it.

These numbers are simulated. Warm-set staleness, prefix caching and real cold-start physics only turn up on hardware, so the next gate is a validation run against real vLLM. That harness is built and tested against a mock, and the GPU run has not happened yet.

satay, up close

Ordinary async code, made durable.

Write your workflow as plain async Python, and every step lands in an append-only journal, so a crashed run picks up where it stopped and you can see exactly what happened. No graph DSL, no hosted service.

import satay

@satay.task(retries=3)
async def fetch(url: str) -> dict:
    # your I/O, your provider SDK calls
    ...

@satay.workflow
async def enrich(urls: list[str]) -> Report:
    pages = await satay.map(fetch, urls, concurrency=8)
    draft = await summarize(pages)
    ok    = await satay.wait_for_event(Approval, key="review")
    return await publish(draft) if ok else draft

How it works

Three ideas, and that's the whole model. Ordinary code, an append-only journal, and replay that reuses what already finished.

01

Write ordinary code

Mark an orchestration function @workflow and the functions it calls @task. Compose them with normal if, for, and try. Your data stays ordinary dicts, dataclasses, and Pydantic models, and your provider calls stay inside tasks.

02

Every step is recorded

Each durable call, with its inputs, output, retries, timers, and model usage, lands in an append-only journal. The journal is the run's single source of truth, and it's plain JSON on SQLite. Nothing is hidden and nothing leaves your machine.

03

Crash, restart, resume

Kill the process mid-run and start it again: satay replays the workflow, hands back the results it already recorded, and runs only the work that never finished. Completed tasks never run twice.

Why not a framework?

Most teams building durable AI workflows reach for an orchestration framework and end up rewriting their app around it. You trade your code for a graph, your exceptions for framework errors, and your debugger for a dashboard you log into. satay takes the other bet: keep your code, add durability underneath it.
